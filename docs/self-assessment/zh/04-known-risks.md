# 4. 已知风险与残余攻击面

> English: [04-known-risks.md (EN)](../04-known-risks.md)

本节对审核者最重要。它诚实地列出当前版本的局限。每条
结构相同:

- **风险** — 可能出什么问题。
- **状态** — *演示可接受* 或 *生产不可接受*(并说明原因)。
- **加固路径** — 若本平台要承载真金白银,具体的下一步。

## R-1. 模拟 MFA

**风险。** MFA 验证使用单一硬编码的 `MFA_DEMO_CODE`
(默认 `000000`,可通过 `MFA_DEMO_CODE` 环境变量配置)。
它运行在进程内,不经外部通道送达。拿到后端访问权的攻击者
可以从内存或环境变量读出它。

**状态。** 演示可接受。**生产不可接受**。

**加固路径。** 接入真实的 OTP 提供方(TOTP 经认证的
TOTP URI,或经有验证送达路径的短信供应商),按用户
注册,按动作 challenge/响应。增加重放保护(单次使用码、
时间戳窗口)。

## R-2. 无真实密钥托管

**风险。** 审计链的 `hash` 仅是上一链 hash 与该行规范化
JSON 拼接后的普通 SHA-256。这是完整性,不是真实性——
任何有数据库写权限的人都可以一致地替换 `prev_hash`
与 `hash` 来扩展链。没有签名密钥、没有 HSM、没有
KMS 签名方。

**状态。** 演示中可接受(数据库本身也是攻击者)。**任何
操作员与外部审计员之间的信任边界都不可接受**。

**加固路径。** 用按部署的密钥(存放在 KMS 中)为每行签名;
只对 hash 签名,不对行内容签名(隐私);公开公钥供离线验证。

## R-3. 无真实卡片 / 银行集成

**风险。** 一切"转账"、"卡片"、"理财持仓"都是 Postgres
中的行。没有轨道集成(无真实卡组织、无 ACH、无 FPS、
无 PSP)。平台能演示**控制面**,不能动真金白银。

**状态。** 已知。README 写明;演示横幅为"仅模拟"。

**加固路径。** 通过合规通道接入合作银行。内部工具白名单
的结构使得新增 `rail.bank.x.*` 命名空间不需要修改规划器
或策略引擎。

## R-4. 提示注入的残余

**风险。** 大模型是聊天体验的前门。防御——固定系统提示、
仅结构化 `proposed_actions`、服务端参数重新解析——是分
层的,但没有提示注入防御是完美的。能在模型上下文(备忘字段、
商户名、收款方别名)中植入文本的高创造力攻击者,可以尝试
胁迫出不安全提案。

**状态。** 已缓解但未消除。红队套件是回归网;新模式发现
时必须加入。

**加固路径。** 把大模型移到一个一次性函数调用接口后面,
配合确定性 schema 解析器;绝不把大模型产生的自由格式文本
与同响应的动作决策混在一起。对 Red 动作,加一个"第二双眼"
层,让另一个模型在执行前验证第一个模型的输出。

## R-5. 前端 / 后端信任边界

**风险。** 前端渲染后端返回的任何状态。被攻陷的后端可以
伪造"转账成功"页面。审计链有帮助,但只是事后。

**状态。** 架构固有——后端是信任根。前端仅做呈现。

**加固路径。** 给每个动作加一个 `receipt` 端点,返回持久化的
`audit_events` 行与结果一起,让 UI 能验证动作确实执行了。
(收据页已经存在;API 是部分的。)

## R-6. 边缘无限流

**风险。** Rust 后端有 12 个 worker 的 actix 运行时,但
`/api/v1/agent/messages` 前没有基于 IP 或基于用户的限流。
有动机的攻击者可以耗尽大模型额度或饿死 DB 连接池。

**状态。** 演示可接受。DB 连接池有 `Pool::acquire` 超时
(10 秒),所以平台是**失败关闭**而非崩溃。

**加固路径。** 在边缘(Envoy / NGINX)加令牌桶限流器,按
用户 id 与 IP 限速,LLM 相关路由使用独立的桶。

## R-7. 权限变更时会话不轮换

**风险。** 在权限变更(例如用户后来被提升为管理员)之前
颁发的会话 cookie 不会被重新颁发。若攻击者偷到旧 cookie,
权限变更对其无效。

**状态。** 未测试。种子用户 `locked_vip` 是演示中唯一角色/
状态会变更的。

**加固路径。** 在 `role`、`safety_lock_state`、`password_hash`
任一变更时轮换 session id。

## R-8. 读端点无 CSRF

**风险。** CSRF token 仅在状态变更请求上要求。读端点 (GET)
按 HTTP 语义是安全的,但通过旁路(缓存、日志)泄露数据的
JSON-bodied 读是可能的。我们当前没发出这种端点。

**状态。** 可接受。

**加固路径。** 给每个端点加 `Sec-Fetch-Site` / `Origin` 白名单
检查,`/api/v1/admin/*` 用严格模式。

## R-9. "预留预算"跨场景流是 Red 级

**风险。** 新增的 `budgets.reserve` 工具把
`available_balance_fen → reserved_balance_fen`,因此是 Red。
聊天智能体的桩已经能产生完整计划("妻子生日,从活期预留
¥1000"),规划器会接受。若用户被社会工程学诱导确认了一个
给陌生收款方的预留,资金会一直被持有,直到释放。

**状态。** 设计如此。风险被金额(上限是大模型抽取的,
用户确认精确数字)与目标可由同一会话内的
`goals.release_reservation` 释放所约束。

**加固路径。** 给任何 label 与已知联系人对不上的目标预留
加"姓名确认"步骤;给任何超过 30 天的预留加"释放"原因要求。

## R-10. 每日限额规则用挂钟,非日历

**风险。** `restrict_daily_fen` 的滚动 24 小时窗口仅在
用户有该时区的会话时才在本地午夜重置。否则平台连续滚动。
这一点有文档但可能让审核者误以为是日历日语义。

**状态。** 已文档化;测试用滚动窗口。

**加固路径。** 增加带显式 `tz` 与 `rollover` 语义的
`daily_window` 规则种类。

## R-11. 审计保留期无界

**风险。** `audit_events` 无 TTL。长期运行的部署会让表
无限增长,`verify_chain` 会越来越慢。

**状态。** 本规模的演示可接受。

**加固路径。** 按月分区,签名包归档到冷存储,加窗口化的
`verify_chain(from, to)` 变体。

## R-12. 审计表在 SQL 层可变(无 DB 级防护)

**风险。** `audit_events` 是一张普通表。没有 `REVOKE
UPDATE, DELETE`,没有 `BEFORE UPDATE` 触发器,没有启用
`pg_temporal` / `pg_audit` 扩展。不可变性是**代码库**属性
而非**数据库**属性。任何有 SQL 写权限的人都可以改写历史。

**状态。** 已知。唯一的护栏是 grep 测试
`! grep -RE 'UPDATE audit_events' src/`。

**加固路径。** 创建只有 INSERT 权限的 `audit_writer` 角色;
让应用以该角色连接,而不是超级用户。加 `BEFORE UPDATE OR
DELETE` 触发器抛错。

## R-13. 大模型桩在仓库内

**风险。** `src/llm.rs::stub_propose` 作为上游大模型不可达
时的确定性回退而存在。它包含 "set a budget"、"妻子生日"
等意图的解析器。未来的贡献者可能在没意识到这是网络故障下
的活跃代码路径的情况下,把它改得更宽松。

**状态。** 桩有文档;`llm.rs` 中的注释把它命名为故障模式
回退。

**加固路径。** 用配置开关门控(`LLM_ALLOW_STUB=1` 仅开发,
生产关闭)。让 CI 在生产构建包含该标志时失败。

## R-14. 优化报告直接读用户交易

**风险。** `routes::accounts.rs` 中的 `report_optimization`
查询在已认证用户的 `transactions` 上做聚合。如果未来某次
改动不小心去掉 `WHERE a.user_id = $1`,报告就会泄露跨用户
数据。

**状态。** 跨用户测试(`tests/cross_user.rs`)覆盖。

**加固路径。** 通过 `for_user(user_id)` 助手集中所有用户
范围查询;加一个 codegen / linter,标记没有 `user_id` 谓词
的裸 `SELECT … FROM transactions`。

## R-15. 对恶意数据库管理员无纵深防御

**风险。** 种子文件随明文的管理员凭据一起发布
(见 `seed.sql`)。MFA 码在环境变量中。审计表可变。若 DBA
恶意,平台完全暴露。

**状态。** [`../../THREAT_MODEL.md`](../../THREAT_MODEL.md) 中
明确将"被攻陷的操作员"列为范围外。本评估也重申这一点。

**加固路径。** 分离只读与写库角色;把审计表放在另一个
数据库实例上,应用只有 INSERT 权限。
